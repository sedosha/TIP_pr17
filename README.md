# Описание границ сервисов

## **Auth Service**

Auth Service отвечает за аутентификацию и управление доступом. Сервис принимает запросы на вход, проверяет учетные данные и выдает токен доступа. Также предоставляет эндпоинт для проверки токена, который используется Tasks Service для авторизации запросов. Хранение учетных данных реализовано в памяти.

## **Tasks Service**

Tasks Service отвечает за управление задачами (CRUD). Сервис позволяет создавать, просматривать, обновлять и удалять задачи. Перед обработкой запроса Tasks Service обращается к Auth Service для проверки валидности токена. Только при успешной проверке запрос передается на обработку. Задачи хранятся в памяти сервиса.

# Список эндпоинтов и кодов ответов

## **Auth Service**

### Эндпоинты

| Метод | Эндпоинт | Описание |
|-------|----------|----------|
| `POST` | `/v1/auth/login` | Получение токена доступа |
| `GET` | `/v1/auth/verify` | Проверка валидности токена |
| `GET` | `/health` | Проверка работоспособности сервиса |

### Коды ответов

| Код | Описание | Когда возникает |
|-----|----------|-----------------|
| `200 OK` | Успешный запрос | Токен получен, токен валиден, health check |
| `400 Bad Request` | Неверный формат запроса | Некорректный JSON при login |
| `401 Unauthorized` | Неавторизован | Неверные учетные данные, отсутствует или неверный токен |
| `503 Service Unavailable` | Сервис недоступен | Внутренняя ошибка сервиса |

---

## **Tasks Service**

### Эндпоинты

| Метод | Эндпоинт | Описание |
|-------|----------|----------|
| `GET` | `/health` | Проверка работоспособности сервиса |
| `POST` | `/v1/tasks` | Создание новой задачи |
| `GET` | `/v1/tasks` | Получение списка всех задач |
| `GET` | `/v1/tasks/{id}` | Получение задачи по ID |
| `PATCH` | `/v1/tasks/{id}` | Частичное обновление задачи |
| `DELETE` | `/v1/tasks/{id}` | Удаление задачи |

### Коды ответов

| Код | Описание | Когда возникает |
|-----|----------|-----------------|
| `200 OK` | Успешный запрос | Получение списка задач, получение задачи по ID, обновление задачи |
| `201 Created` | Ресурс создан | Задача успешно создана |
| `204 No Content` | Нет содержимого | Задача успешно удалена |
| `400 Bad Request` | Неверный формат запроса | Некорректный JSON при создании/обновлении |
| `401 Unauthorized` | Неавторизован | Отсутствует токен, неверный формат токена, неверный токен |
| `404 Not Found` | Не найдено | Запрос задачи по несуществующему ID |
| `503 Service Unavailable` | Сервис недоступен | Auth Service не отвечает (таймаут 3 секунды) |

# Контрольные вопросы
1.	Почему межсервисный вызов должен иметь таймаут? Таймаут необходим, чтобы сервис не зависал бесконечно в ожидании ответа от другого сервиса, что может привести к исчерпанию ресурсов и каскадным отказам. Без таймаута один зависший сервис может заблокировать все входящие соединения и парализовать работу всей системы.
2.	Чем request-id помогает при диагностике ошибок? Request-id позволяет связать воедино все запросы, проходящие через разные сервисы в рамках одной бизнес-операции. Это дает возможность отследить полный путь прохождения запроса, понять в каком именно сервисе произошла ошибка и измерить время выполнения каждого этапа.
3.	Какие статусы нужно вернуть клиенту при невалидном токене?  При невалидном токене клиенту нужно вернуть статус 401 Unauthorized с понятным сообщением об ошибке. Это сигнализирует клиенту, что ему необходимо получить новый токен или предоставить корректные учетные данные.
4.	Чем опасно “делить одну БД” между сервисами? Общая БД создает жесткую связь между сервисами, лишая их независимости в выборе технологий и возможности масштабироваться по отдельности. Изменение схемы данных для одного сервиса может сломать другой, что противоречит самой идее микросервисной архитектуры.
